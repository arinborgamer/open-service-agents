# v0.3: choose, revise and package a product

This release closes specific workflow gaps in the public demonstrations: outline selection before full generation, AI-assisted regeneration with review, usable product-page starting points, and delivery of the PDF alongside editable editions. It does not reproduce a private lead database, managed sending infrastructure, proprietary training, paid coaching or guaranteed results. See the [current primary-source comparison](research/suite-upgrade.md).

## Use the upgraded studio

1. Open `/studio`, unlock it, and fill in **Product studio**. The default workflow is **Compare three outlines first**. The original direct-draft option is still available.
2. Open **Plans & revisions**. The worker generates a practical guide, an exercise-led workshop and a troubleshooting playbook, saving each separately. You can close the tab while it works. The page polls while tasks are active. Three outlines are suggestions, not proof of demand.
3. Read the alternatives and choose **Build this outline**. The saved selection becomes the exact transformation artifact and guides the chapter prompts. Repeating the same selection returns the same job. Choosing another alternative creates a separate draft.
4. Open a completed draft and choose **Review quality & sources**. The report shows chapter word counts, missing/duplicate chapters, possible placeholders and which chapters cite each supplied source. This is a structural review, not a claim verifier or quality score.
5. Expand a section and choose **Ask AI to revise**. Describe the change, then compare the full original and proposed replacement in **Plans & revisions**. **Save this revision** is the only action that changes the draft. A suggestion cannot overwrite intervening manual edits or an approved product. Prior content remains in revision history.
6. To update something already approved, choose **Create a new edition**. This makes a separate editable draft with the same provider and contents. Existing product IDs and buyer entitlements keep the old edition. Approve the new edition under a new product ID after review.
7. In **Store & orders**, choose an approved product and an original page template. Preview the suggested copy before inserting it into the editor. Guide, workbook and curriculum templates use that edition's actual outline, chapter titles and sample. They never invent seller information or silently publish. Inserting a template replaces unsaved copy fields and sections; review and save it yourself.
8. Use **Download PDF** or **Download product**. Install `pip install -e '.[pdf]'` to enable PDF output. With PDF support installed, customer ZIPs include `product.pdf`, `product.html`, `product.md`, `CONTENTS.json` and a README. Without it, the archive explicitly lists HTML/Markdown only and the standalone PDF request fails clearly. A renderer error does not silently substitute a different edition. Keep PDF support installed if you advertise that format.

Course/coaching formats remain written resources; no videos or coaching sessions are created. The HTML/Markdown/PDF editions still require editorial review. The customer package excludes raw source notes, creator contacts, outreach drafts and operator-only analyses.

## Persistence and runtime

Existing SQLite databases gain an additive `creative_tasks` table. Jobs, orders, approvals and configuration are retained. There is no new hosted service or required AI subscription. The same `osa worker` handles creative tasks before manuscript jobs. Each outline is checkpointed; tasks have leases, bounded retries and sanitized failure messages. Failed tasks can be retried from saved progress. Large revision inputs are rejected with instructions to use the manual editor rather than silently truncating the section.

Restart the local supervisor after updating. Python remains the runtime; Docker is still an optional deployment template. Install PDF support on every server that serves customer downloads.

## API additions

All of these routes require the operator bearer token:

| Route | Purpose |
| --- | --- |
| `GET /v1/creative` | List the last 50 outline/revision tasks and saved results |
| `POST /v1/creative/outlines` | Queue three alternatives using `brief` and `provider` |
| `POST /v1/creative/select` | Start a manuscript from task `id` and `variant` |
| `POST /v1/creative/revision` | Queue `job_id`, `stage`, matching `provider` and `instruction` |
| `POST /v1/creative/apply` | Save a completed revision by task `id`, only if the original still matches |
| `POST /v1/creative/retry` | Retry a failed creative task by `id` |
| `POST /v1/jobs/fork` | Copy completed job `id` into an editable edition |
| `GET /v1/quality/JOB_ID` | Structural chapter and source review |
| `GET /v1/templates` | List original storefront template descriptions |
| `POST /v1/storefronts/template` | Return unsaved copy for `product_id` and `template_id` |
| `GET /v1/pdf/JOB_ID` | Download the current completed edition as a PDF |

Outline variants are `field-guide`, `workshop` and `playbook`. Storefront templates are `field-guide`, `workbook` and `curriculum`.

## Verification

Run `python -m unittest discover -s tests -v`. For the browser workflow, start `python tests/qa_server.py` and run `node tools/qa_studio.cjs` in another terminal with Playwright available. Set `OSA_QA_BROWSER=msedge` if using an installed Edge instead of Playwright's Chromium. The server is bound to loopback and uses fictional fixtures with outgoing credentials removed. Its short worker exists only for testing.

`python tools/smoke_creative.py` performs three actual local-Ollama calls in disposable state. It never contacts a customer or starts a payment. A successful result validates the model/schema path, not factual accuracy, publishability, customer demand or income.
