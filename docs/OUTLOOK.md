# Personal Outlook.com connection

This adapter adds Microsoft OAuth to the existing SMTP sender and read-only IMAP reply monitor. It is not the Outlook plugin for this chat and does not use Microsoft Graph. Graph remains a reasonable future adapter; protocol OAuth was selected here to preserve the existing Message-ID correlation and delivery queue. Microsoft supports protocol OAuth for personal accounts. [Microsoft protocol OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)

No mailbox is connected merely by installation. Passwords and app passwords are not used for this connection. Never paste passwords, login tokens or bank details into chat, GitHub or the dashboard. Recipients see the sender address: use a separate brand mailbox if the personal address identifies you. This does not provide anonymity from Microsoft or payment providers.

## 1. Owner creates a public-client registration

Microsoft's current registration guide lists an Azure account/subscription, tenant and sufficient developer permissions as prerequisites. An Outlook.com mailbox alone does not establish registration access. If the portal requires onboarding, payment details or terms you have not reviewed, stop and decide whether to proceed yourself; do not weaken security controls. [Registration prerequisites](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app)

In the [Microsoft Entra admin center](https://entra.microsoft.com), go to **Entra ID > App registrations > New registration**. Use an original name such as **Open Service Agents Local**, select **Personal accounts only**, and register it. Record the **Application (client) ID**, a non-secret identifier. Under the app's Authentication settings, configure a **Mobile and desktop application** redirect URI of **http://localhost**. Do not create a client secret: this is a public desktop client. [Registration](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [MSAL browser login / PKCE](https://learn.microsoft.com/en-us/entra/msal/python/getting-started/acquiring-tokens)

The application requests delegated `https://outlook.office.com/SMTP.Send` at sign-in. Optional reply monitoring additionally requests `https://outlook.office.com/IMAP.AccessAsUser.All`. These are Outlook-resource permissions, not Graph `Mail.Send` and not application-wide `SMTP.SendAsApp`. MSAL also requests its normal OpenID/offline scopes. Review the actual consent screen; decline if the app or permissions do not match. Inbox permission technically covers mailbox access, not only the threads generated by the agent. The code separately restricts imports to matching senders and Message-IDs. [Scopes and refresh access](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)

## 2. Configure locally, with sending still disabled

Install `pip install -e ".[outlook]"` in the project virtual environment. Add these values to the private `.local/runtime.env`; do not replace its generated API/download/webhook secrets:

```dotenv
OSA_MICROSOFT_CLIENT_ID=YOUR-APPLICATION-CLIENT-ID
OSA_MAIL_AUTH=microsoft
OSA_FROM_EMAIL=your-primary-mailbox@outlook.com
OSA_SMTP_USER=your-primary-mailbox@outlook.com
OSA_SMTP_HOST=smtp-mail.outlook.com
OSA_SMTP_PORT=587
OSA_SMTP_PASSWORD=
OSA_MAIL_ENABLED=false
OSA_IMAP_ENABLED=false
```

The sender and sign-in mailbox must match the primary account username. Arbitrary sender aliases/shared mailboxes are not supported. Restart existing workers so they see the disabled flags before connecting. An already-running worker retains its previous environment.

Run these locally as the same operating-system user who runs the agents:

```sh
osa outlook-connect
osa outlook-verify
osa outlook-status
```

The first opens Microsoft's browser sign-in with PKCE and waits up to three minutes for the owner. The second authenticates SMTP and issues NOOP, without sending an email or reading the inbox. The third only reports configuration/cache-file presence; it does not verify current authorization. Neither command enables sending.

Tokens are persisted using Microsoft's encrypted cache library outside the repository: Windows LocalAppData uses DPAPI, macOS uses Keychain, Linux requires working LibSecret. Plaintext fallback is forbidden. Headless containers without an OS secret store are not supported by this adapter. Do not copy the cache to GitHub, a public host or another operating-system account. Workers use silent refresh only; revocation/expiry requires the owner to reconnect. [Encrypted persistence](https://github.com/AzureAD/microsoft-authentication-extensions-for-python)

## 3. Optional reply monitoring

While both flags are still false, run `osa outlook-connect --with-inbox` and separately review the broader mailbox permission. In Outlook.com, use **Settings > Mail > Forwarding and IMAP** to enable IMAP access if desired. Configure:

```dotenv
OSA_IMAP_AUTH=microsoft
OSA_IMAP_HOST=outlook.office365.com
OSA_IMAP_PORT=993
OSA_IMAP_USER=your-primary-mailbox@outlook.com
OSA_IMAP_PASSWORD=
OSA_IMAP_FOLDER=INBOX
```

Enable `OSA_IMAP_ENABLED=true` only after approval and restart the mail worker. Read-only selection and BODY.PEEK leave messages unread; only correlated replies are imported. Permission to access the mailbox remains broader than that application filter. Inbox-only monitoring misses replies moved to other folders. [Microsoft personal-mail settings](https://support.microsoft.com/en-us/outlook/pop-imap-and-smtp-settings-for-outlook-com)

## 4. Controlled sending test and revocation

First inspect `osa mail-queue` and make sure no unintended messages are approved. Draft one clearly labelled test addressed to your own mailbox, approve only that draft, then enable `OSA_MAIL_ENABLED=true` and restart the worker. Enabling this flag releases **all due approved messages**, not just the test. Check actual receipt before using any outreach workflow. A successful SMTP submission is not guaranteed recipient delivery.

Keep the low daily cap and per-message review. Use genuine contact evidence, stop follow-ups on replies/opt-outs, and never treat a personal mailbox as a bulk unsolicited-marketing service. No customer acquisition or revenue is created by connecting it.

To stop access, disable the mail/inbox flags and restart workers, then revoke this application's permissions in your Microsoft account. A saved local cache can exist after revocation; the next silent request must fail and require sign-in. Do not change Microsoft tenant security defaults to make this personal-account adapter work.

## Validation boundary

OAuth selection, exact-account filtering, endpoint restrictions, fail-closed refresh, separate inbox consent, no-send verification and read-only IMAP behavior are covered with mocks. Local Windows encrypted-persistence checks are separate from live authentication. No real Microsoft app registration, owner consent, mailbox read or email delivery was performed during implementation.
